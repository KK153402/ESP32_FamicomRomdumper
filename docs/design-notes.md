# 設計ノート / Design Notes

このROMダンパーの設計判断の理由と、技術的な背景をまとめた文書です。部品表と接続は [hardware.md](hardware.md)、手順は [bringup.md](bringup.md) を参照してください。

---

## 1. 全体方針

### 1.1 なぜFPGAではなくESP32なのか

ファミコンのカセットに載っているマスクROMは**完全スタティック**です。アドレスを与えて出力を有効にすれば、何秒待っても同じデータを出し続けます。ファミコン本体はCPUサイクル559 ns、PPU読み出しの窓は約372 nsで動いていますが、これは本体側の都合であって、ROMを読むだけならクロックに合わせる必要はありません。

したがって、ダンパーには速度要件がありません。1 kHzで読んでも正しく読めます。この性質を使うと、以下の設計が可能になります。

- 54本のバス信号をシフトレジスタで圧縮し、MCUのGPIO数の制約を回避する
- 汎用MCU（ESP32）とUSBシリアルだけでPCへ転送する

リアルタイムでカセットを駆動する必要がある場合（カセットを挿してそのままゲームを動かす機械）は、PPUの372 nsの窓に間に合わせるためFPGAが必要になります。このダンパーは、その前段階として「カセットのバスを正しく扱えること」を確認する位置づけでもあります。

### 1.2 カセットバスの概要

60ピンのファミコンカセットは、2つの独立したバスを持っています。

| バス | 信号 | 本数 | 内容 |
|---|---|---|---|
| CPUバス | A0〜A14、D0〜D7、M2、/ROMSEL、R/W、/IRQ | 27 | PRG-ROM（プログラム）へのアクセス |
| PPUバス | PA0〜PA13、PD0〜PD7、/RD、/WR、/A13、CIRAM A10、CIRAM /CE | 27 | CHR-ROM（画像データ）へのアクセス、画面用RAMの制御 |

ポイントは以下の3つです。

- **CPUバスにA15は出ていません。** 代わりに `/ROMSEL` = NOT(A15 AND M2) が出ています。`$8000`〜`$FFFF` を読むには、A0〜A14を出してM2 = H、/ROMSEL = L にします
- **CIRAM A10 はカセットからの出力です。** 本体の画面用RAM（2 KB）のアドレスA10をカセットが決めることで、ミラーリング（画面の繋がり方）をカセット側が選べる仕組みです
- ピン間隔は **2.54 mm（0.1インチ）** です。海外版NES（72ピン）の2.50 mmとは異なり、汎用のカードエッジコネクタと同じピッチです

## 2. ピン数の圧縮

### 2.1 構成

| 用途 | 本数 | 方式 | ESP32側のピン数 |
|---|---|---|---|
| アドレス（CPU 15 + PPU 14） | 29 | 74AHCT595 × 4 のデイジーチェーン | 共通 |
| データ書き込み（CPU 8 + PPU 8） | 16 | 74AHCT595 × 2 のデイジーチェーン | 共通 |
| データ読み出し（CPU 8 + PPU 8） | 16 | 74HCT165 × 2 のデイジーチェーン | 共通 |
| シフトレジスタの共通線 | — | SCK、MOSI、MISO、RCLK × 2、/OE × 2、/PL | 8 |
| 制御線 | 6 | 74AHCT244 経由で直接 | 6 |
| CIRAM | 2 | 74LVC1T45 経由で直接 | 2 |
| **合計** | **54 + 保護** | | **16** |

アドレス系とデータ系の595は、SCK（シフトクロック）とMOSI（シリアルデータ）を共有しています。出力を更新するタイミング（RCLK）だけを分けているので、片方に送ったデータがもう片方の出力に現れることはありません。

### 2.2 デイジーチェーンのバイト順

595はチェーンの先頭から順にデータが押し出されるため、**最初に送ったバイトがチェーンの末尾のICに到着します**。MSBファーストで送ると、bit7がQH、bit0がQAに対応します。

アドレス系のチェーンは MOSI → U1 → U2 → U3 → U4 なので、送る順番は逆になります。

| 送信順 | 到着するIC | 内容 |
|---|---|---|
| 1バイト目 | U4 | `{00, PA13..PA8}` |
| 2バイト目 | U3 | `{PA7..PA0}` |
| 3バイト目 | U2 | `{0, A14..A8}` |
| 4バイト目 | U1 | `{A7..A0}` |

165は逆方向で、U8 → U7 → MISO の順にチェーンされているので、最初に受け取るバイトがU7（CPUデータ）、次がU8（PPUデータ）です。

### 2.3 165のパラレル入力の割り当て

165は **A → B → C → … → H → QH** の方向にシフトします。つまり、ロード直後にQHに出ているのは**Hピンの値**で、最初に受信されます。MSBファーストで受信するとき最初のビットがbit7なので、**Hピン（6番）にD7、Aピン（11番）にD0**を接続します。

165のピン番号はA〜Dが11〜14、E〜Hが3〜6と飛んでいるため、回路図で取り違えやすい箇所です。実際に設計段階で、ピン11〜14を逆順に接続するミスが2回発生しました。この場合、上位4ビットは正常なまま下位4ビットだけが反転するので、値をぱっと見ても気づきにくい壊れ方をします。

## 3. レベル変換の考え方

ESP32は3.3 V、カセットのROMとマッパーは5 Vで動作します。54本すべてにレベル変換ICを入れると部品が増えるため、ロジックICの入力しきい値を使って大半を省略しています。

### 3.1 シフトレジスタを5Vで動かす

**74HCT / 74AHCT シリーズは、5 V電源で動作しながら入力しきい値がTTLレベル（VIH = 2.0 V）です。** 3.3 Vの信号をそのままHとして受けられ、出力は5 Vで振れます。

| シリーズ | VCC = 5 V時のVIH（Hと判定される最低電圧） | ESP32の出力（VOH ≧ 2.64 V）を受けられるか |
|---|---|---|
| 74HC | 約3.5 V（0.7 × VCC） | ✗ |
| 74AHC | 約3.5 V（0.7 × VCC） | ✗ |
| 74HCT | 2.0 V | ✅ 余裕0.64 V以上 |
| 74AHCT | 2.0 V | ✅ 同上 |

ESP32のVOHはデータシート上 0.8 × VDD = 2.64 V（最小値）です。実際の出力はほぼ3.3 Vなので、HCT/AHCTのVIH 2.0 Vに対して十分な余裕があります。

**型番末尾の「T」が決定的に重要です。** 74HC595や74AHC595を使うと、3.3 Vの入力がHと判定されず、回路が成立しません。

入手性の都合で、595はHCTではなくAHCT（SN74AHCT595D）を使っています。AHCTはHCTと同じTTLしきい値を持ち、伝搬遅延はHCTより短く（数ns〜十数ns）、ピン配置も同一なので、置き換えて問題ありません。一方でAHCTは立ち上がりが速い分、多数の出力が同時に切り替わるときの電源の揺れが大きいので、各ICのパスコン（0.1 µF）を最短で配置し、10 µFのバルクコンデンサも置いています。

なお、AHCTファミリには165がないため、読み出し側はHCT（CD74HCT165）です。HCTとAHCTは同じ電源・同じしきい値なので混在して問題ありません。

### 3.2 制御線を74AHCT244で受け直す理由

595の出力は5 V CMOSレベルで振れるので、カセットへそのまま出せます。一方、ESP32から直接出す制御線（M2、/ROMSEL、R/W、/RD、/WR、/A13）は3.3 Vです。カセット上のマッパーICや5 V CMOSロジックの入力しきい値はVCC = 5 Vで約3.5 Vなので、3.3 Vでは確実にHと判定されません。

そこで、この6本だけを74AHCT244（TTLしきい値入力、5 V出力）で受け直しています。

### 3.3 5 V → 3.3 V方向

ESP32の入力は5 Vトレラントではありません。カセットからESP32に向かう信号は以下の3本だけで、それぞれ74LVC1T45（VCCA = 3.3 V、VCCB = 5 V、DIR = GND でB→A固定）で降圧しています。

- 165のシリアル出力（QH）→ MISO
- CIRAM A10 → GPIO34
- CIRAM /CE → GPIO35

いずれも速度要件が低いので、抵抗分圧でも代替できます。3.3 kΩ + 6.8 kΩの場合、5 V × 6.8 / (3.3 + 6.8) = 3.37 V で、ESP32のVIH（0.75 × VDD = 2.48 V）を満たします。

## 4. バスの保護設計

### 4.1 CPUデータバスとPPUデータバスの分離

データ書き込み用の595は、CPU側（U5）とPPU側（U6）に分けています。1個の595の出力をCPU D0〜D7とPPU D0〜D7の両方に接続すると、2本の独立したバスが恒久的に短絡します。ダンプ動作だけなら書き込みを使わないので問題が表面化しにくいですが、カセット側がデータバスを駆動したときにバス競合が起きます。

### 4.2 カセット電源の独立（`VCC_CART`）

カセットの抜き差しのため、スイッチ（SW1）でカセットの電源を切れるようにしています。このとき**遮断するのはカセットの電源だけ**で、基板上のロジックICは常時給電のままにします。

基板全体の5 Vを切ると、ESP32（USBから給電され動き続ける）が電源の落ちたICの入力に3.3 Vを加える状態になります。入力保護ダイオード経由でICの電源ラインに電流が流れ込み、ICが中途半端に動作したり、ラッチアップの原因になります。

### 4.3 バスのHi-Z化（`BUS_EN_N`）

カセットの電源だけを切っても、595と244は5 Vを出力し続けます。今度は電源の落ちたカセットのICに、アドレス線経由で電流が流れ込みます。

これを防ぐため、アドレス出力（U1〜U4）と制御線（U9）の出力イネーブル（/OE）をまとめて1本のGPIO（`BUS_EN_N`）で制御しています。

```
カセットを抜く：  BUS_EN_N = H（Hi-Z） → SW1 OFF → 抜く
カセットを挿す：  挿す → SW1 ON → BUS_EN_N = L（有効）
```

`BUS_EN_N` は10 kΩで3.3 Vにプルアップしているので、ESP32の起動中やリセット中は自動的にHi-Zになります。74AHCTの/OE入力もTTLしきい値なので、3.3 VでHと判定されます。

### 4.4 プル抵抗の配置

Hi-Zにした線や、ESP32のリセット中にGPIOが浮いた線の電圧を確定させるため、プル抵抗を両側に置いています。

| 位置 | プル先 | 目的 |
|---|---|---|
| 244の入力側（3.3 V側）6本 | +3.3 V（M2のみGND） | ESP32のリセット中、244の入力が浮いてカセットへ不定な信号が出ないようにする |
| 244の出力側（5 V側）6本 | `VCC_CART`（M2のみGND） | `BUS_EN_N` でHi-Zにしたとき、カセット側の制御線を非アクティブに保つ |
| データバス16本 | `VCC_CART` | 何も駆動していないバスを `$FF` として読む（オープンバスの検出） |
| CIRAM 2本 | `VCC_CART` | カセット未挿入時に74LVC1T45の入力が浮かないようにする |

**カセット側のプル抵抗は `+5V` ではなく `VCC_CART` に接続しています。** `+5V` に接続すると、SW1を切っても各抵抗からカセットの入力保護ダイオード経由で電流が流れ込みます。

(5 V − 0.6 V) ÷ 10 kΩ ≒ 0.44 mA/本、21本で最大約9 mA

この電流でカセットの電源ラインが弱く持ち上がり、電源を切ったつもりでもカセットが中途半端に通電した状態になります。`VCC_CART` に接続すれば、カセット通電中の動作はまったく同じで、電源を切ればプル抵抗も一緒に落ちます。

**244の出力側のプル先を3.3 Vにしてはいけません。** Hi-Z時にカセット側の線が3.3 Vになり、5 V CMOSのVIH（約3.5 V）を満たさない不定領域に入るためです。

**74LVC1T45の入力を浮かせてはいけません。** CMOS入力が中間電位に浮くと入力段に貫通電流が流れ、消費電流の増加や発振の原因になります。CIRAMの2本は、カセット未挿入時に接続先がコネクタのパッドだけになるため、プルアップが必要です。

## 5. 読み出しシーケンス

### 5.1 PRG-ROM（CPUバス）

```
1. 595でアドレス A0〜A14 を出力（RCLK_ADDRで確定）
2. R/W = H、M2 = H、/ROMSEL = L     ← $8000〜$FFFF が選択される
3. 2 µs 待つ
4. /PL をパルス → 165にデータバスをロード
5. 165を16ビット読み、先頭8ビットをCPUデータとする
6. /ROMSEL = H、M2 = L
```

当時のマスクROMのアクセスタイムは150〜250 ns程度なので、2 µsの待ち時間は8倍以上の余裕があります。

### 5.2 CHR-ROM（PPUバス）

```
1. 595でアドレス PA0〜PA12 を出力（PA13 = 0）
2. /A13 = H、/RD = L
3. 2 µs 待つ
4. /PL をパルス → 165にロード
5. 165を16ビット読み、後半8ビットをPPUデータとする
6. /RD = H
```

### 5.3 ミラーリングの判定

NROMカセットでは、CIRAM A10がカセット基板上でPPU A10かA11に直結されています。PPUアドレスを `$2400`（PA10 = 1）と `$2800`（PA11 = 1）にして、CIRAM A10がどちらに追従するかを見れば判定できます。

| CIRAM A10 が追従 | ミラーリング |
|---|---|
| PA10 | 垂直（左右の画面がつながる。横スクロールのゲーム） |
| PA11 | 水平（上下の画面がつながる） |

### 5.4 PRG容量の判定

NROM-128（PRG 16 KB）のカセットはA14を使わないため、`$8000`〜`$BFFF` と `$C000`〜`$FFFF` に同じ内容が見えます。両者を比較して一致すれば16 KB品と判定します。

## 6. 74HC165の読み出しとビットバング

### 6.1 起きた問題

最初のファームは、ESP32のハードウェアSPI（MODE0、1 MHz）で165を読んでいました。カセット未挿入でデータバスがすべてH（プルアップ）の状態なのに、以下の値が返りました。

```
CPU D=FF  PPU D=FE       ← 期待値は FF FF
```

### 6.2 原因の特定

この回路で「0」が出てくる場所は1つしかありません。**チェーン末尾のU8のシリアル入力（SER）がGNDに接続されている**ことです。165はクロックを1回余分に進めると、末尾にSERの値が入ってきます。

```
正しい読み：  [U7: H G F E D C B A] [U8: H G F E D C B A]    → FF FF
1ビットずれ：  [U7: G F E D C B A][U8: H] [U8: G F E D C B A][SER=0]  → FF FE
```

つまり、**先頭ビット（U7のH = CPU D7）を読む前にシフトが1回起きて、そのビットを失っていた**ことになります。データがすべて1なので、ずれの影響が末尾の0としてだけ見えていました。

### 6.3 仕組み

165は、/PLでロードした直後から最初のビット（H）をQHに出していて、CPの**立ち上がり**でシフトします。SPI MODE0は、同じ**立ち上がり**でMISOを取り込みます。

165のシフト（CP → QH の伝搬遅延）と、ESP32がMISOを取り込むタイミングが同じクロックエッジで競合します。観測結果から、ESP32はシフト後の値を取り込んでいたと判断できます。

### 6.4 対策

SPI MODE2（クロックの待機レベルがH、立ち下がりで取り込み）に変えれば165の読み出しは正しくなりますが、今度は595への書き込み側で、MOSIの変化と595の取り込み（立ち上がり）が同じエッジで競合します。読み出しと書き込みでSPIモードを切り替える方法もありますが、モード切替時にクロックの待機レベルが変わること自体がエッジになり、別の問題を起こします。

そこで、**ハードウェアSPIをやめて、GPIOでクロックを1ビットずつ操作する（ビットバング）方式**に変更しました。

```cpp
uint8_t shiftInByte() {
  uint8_t v = 0;
  for (int i = 0; i < 8; i++) {
    v = (v << 1) | digitalRead(PIN_MISO);   // 先に読む
    sclk();                                 // それからシフト
  }
  return v;
}
```

「QHを読んでからクロックを上げる」順番がコードで固定されるので、タイミング競合が原理的に起きません。

### 6.5 速度

| 処理 | 計算 | 時間 |
|---|---|---|
| シフトクロック1回 | 半周期1 µs × 2 + GPIO操作 | 約2.3 µs |
| 1バイト読み出し | アドレス32クロック + 読み出し16クロック + 待ち約5 µs | 約110 µs |
| 40 KB 読み出し | 110 µs × 40960 | 約4.5 秒 |
| 40 KB 転送 | 115200 bps ÷ 10 bit = 11.52 KB/s | 約3.6 秒 |

実測では1回あたり11.5秒（読み出し、転送、判定処理を含む）でした。ダンパーとしては十分な速度です。

## 7. ダンプの信頼性

カセットの端子は30年以上前のもので、接点不良が起きやすい部品です。接点不良は「毎回同じ値が化ける」のではなく「たまに化ける」形で現れるため、1回読んだだけでは気づけません。

PC側スクリプトは以下の2段階で確認しています。

1. **転送の確認**：ESP32側とPC側で CRC-32 を計算して照合（USBシリアル転送の化けを検出）
2. **読み出しの確認**：カセットを2回ダンプして、PRG・CHR・ミラーリングがすべて一致した場合のみ保存（接点不良による化けを検出）

## 8. 回路図レビューで見つかった設計ミス

基板発注前のネットリストのレビューで、以下のミスが見つかり修正しました。**いずれもKiCadのERC（電気的ルールチェック）では検出できません。** ネットリストを出力して、人の目で確認する必要があります。

| ミス | 放置した場合の結果 | 教訓 |
|---|---|---|
| 244の入力側と出力側が同じネット名で短絡 | ESP32のGPIOがカセットの5 Vラインに直結されて壊れる | バッファの入出力は必ず別名（`M2_3.3V` / `M2_5V`）にする |
| 165のピン11〜14が逆順 | 下位4ビットだけが反転する | 165はピン番号とビット順が直感に反する |
| 244の/OE（ピン1）が未接続 | 出力が不定になる | 未接続ピンの一覧（`unconnected-`）を全部読む |
| RCLK_DATAをGPIO3に割り当て | GPIO3はUART0の受信ピンで、書き込みもシリアル通信もできなくなる | ESP32のGPIO1/3は使わない |
| 244出力側のプル先が3.3 V | Hi-Z時にカセット側が不定電位になる | プル先の電圧は、受ける側のしきい値で決める |
| カセット側のプル先が `+5V` | 電源を切ったカセットに電流が流れ込む | 遮断する電源に繋がる信号のプル先も一緒に遮断する |
| CIRAMのレベル変換入力が浮く | カセット未挿入時にLVC入力が浮く | 「片側がコネクタのパッドだけ」の入力ピンを探す |
| ネット名の `/` | KiCadで `{slash}` に化ける | 負論理は `_N` で表す |

## 9. 立ち上げで分かったこと

実機での立ち上げ時に、以下のような「故障に見えるが故障ではない」現象がありました。いずれも設計どおりの動作です。

| 現象 | 原因 |
|---|---|
| データ線の電圧が約2.8 V | SW1 OFFでプルアップの電源（`VCC_CART`）がなく、線が浮いていた。浮いたCMOSノードをテスタで測ると意味のない中間電圧が見える |
| 制御線のうちM2だけ5 Vにならない | `E 0` を送っておらず、244がHi-Zだった。M2以外の5本は出力側プルアップで5 Vに見えていた（M2だけプルダウン） |

後者は、**`E 0` を送らないまま「5 Vが出た」ことだけを確認すると、ほかの5本も正常に見えてしまう**という点で注意が必要です。制御線の確認では、0 Vに落ちることを必ず確認します。

また、ジャンパー線がなくても回路の正しさを確認できる「既知の値」がいくつもありました。

| 既知の値 | 確認できること |
|---|---|
| U8のSERがGND | 165の読み出しのビットずれ |
| 割り込みベクタが `$8000` 以上 | CPUアドレス線・データ線・制御線 |
| ほとんどのソフトの先頭命令が `78 D8`（SEI、CLD） | データ線のビット順 |
| NROMのCIRAM A10はPA10かPA11に直結 | PPUアドレス線とCIRAM経路 |

## 10. 今後の拡張

| 項目 | 内容 |
|---|---|
| UNROM対応 | `$8000`〜`$FFFF` への書き込みでバンク切替。ROMとの**バス競合**があるため、書き込む値がROM上のその番地の値と一致している必要がある |
| MMC1対応 | 5回のシリアル書き込みでレジスタを設定。連続するCPUサイクルの書き込みは無視されるため、書き込みの間にM2を1サイクル以上入れる |
| MMC3対応 | `$8000`/`$8001` でバンク選択と値を設定 |
| CHR-RAM判定 | CHR領域に書き込んで読み戻せればRAM（iNESヘッダのCHRサイズを0にする） |
| バッテリーバックアップSRAM | `$6000`〜`$7FFF`。/ROMSEL = H の領域で、M2で有効になる |
| マッパー自動判定 | 吸い出したデータのCRCを既知のデータベースと照合する |
| 高速化 | シリアルのボーレートを上げる（ESP32のUSBシリアル変換ICの上限まで） |
